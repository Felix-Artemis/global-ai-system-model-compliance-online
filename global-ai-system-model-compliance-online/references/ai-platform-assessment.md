# AI平台三层评估路由

本文件把本 Skill 的输出固定为一个统一的 AI 平台合规评估，而不是一般性数据传输审计。所有问题都应回到被评估的 AI 平台、模型、应用界面、内容流转和实际数据流。

## 三层结构

### 第一层：三地 AI 透明度核心

默认并行评估中国大陆、欧盟和美国加州的生成合成内容标识、机器可读标记、交互告知、深度伪造披露、检测或验证工具、内容传播链路和适用日期。中国大陆是默认入口，因为多数使用者位于中国大陆；用户可以在入口自测表中缩小或扩展法域，但不得因此漏掉已经明确存在的连接点。

### 第二层：欧盟 AI Act 扩展核心

只要用户选择欧盟或事实显示系统、模型或输出在欧盟投放市场、投入使用或被使用，就询问并可分别启动两个子评估：

1. 系统层初筛：先判断是否可能涉及 Article 5 的不可接受风险或禁止性 AI 实践，再判断是否可能属于 Article 6(1) Annex I 嵌入产品高风险、Article 6(2) Annex III 独立系统高风险，或 Article 6(1) 与产品法规共同适用的情形。该初筛不是最终法律意见；不确定事实用“若事实成立则触发”的条件式表达，并提示需要专项高风险评估。
2. 模型层初筛：判断是否为 general-purpose AI model（GPAI），以及是否可能达到具有 systemic risk 的 GPAI 门槛。核对 AI Act 第三条、第五章和现行合并版文本，逐项记录模型训练、泛化能力、下游用途、计算量和指定状态；不得把应用层调用 API 自动写成 GPAI provider。

系统层和模型层是第二层核心功能，报告应分别列明：事实、初筛结果、适用或预计适用日期、需要补充的证据、最严重后果和是否需要专项法律评估。

### 第三层：AI 平台附属评估

仅在用户选择或 AI 平台数据流出现相关连接点时，评估 GDPR、EUDPR、CCPA/CPRA、跨境传输和美国敏感数据限制。该层不替代隐私影响评估或完整数据保护审计，也不把服务器所在地简单等同于合规结论。

跨境评估应当按处理活动建立角色矩阵：

| 事实要素 | 需要核实的内容 | 可能的角色结论 |
|---|---|---|
| 目的决定 | 谁决定收集、生成、训练、客服、分析和保留目的 | GDPR controller、joint controller，或 California business |
| 手段决定 | 谁决定模型、字段、提示词、访问权限、保留和安全措施 | controller 或 processor；只凭合同名称不能定性 |
| 指令与独立权限 | 是否仅按客户书面指令处理，是否自行用于改进模型、广告或画像 | processor/service provider/contractor，或独立 controller/business |
| 访问链路 | 上游模型方、云厂商、客服外包、监控服务是否可访问数据 | processor、subprocessor、service provider 或第三方接收方 |
| 再转移 | 支持人员远程访问、备份、日志、灾备和 onward transfer 的目的地 | GDPR 第五章传输连接点；美国限制规则的 covered data transfer 风险 |
| 加州商业目的 | 是否出售或共享个人信息、定向广告、跨情境行为广告，是否仅为业务目的提供服务 | CCPA business、service provider、contractor 或 third party |

报告只在这些事实与 AI 平台处理活动直接相关时给出附属评估；若用户未选择第三层，正文写“未启动附属评估”，并列出可能触发的连接点，不扩展成一般性 GDPR/CCPA 意见。

## 效力标签

每条结论必须带下列标签之一：

| 标签 | 含义 | 输出方式 |
|---|---|---|
| 强制性法规 | 条约、法规、指令、国内法、已生效修正及其 Official Journal 文本 | 可以作为法定义务依据；写明生效或适用日期和最严重后果 |
| 官方解释性材料 | Commission、AI Office、AI Board、EDPB、EDPS、Service Desk 指南、FAQ、模板 | 解释或实务参考，不单独创设法定义务 |
| 欧盟建议的良好实践 | Code of Practice、vademecum、签署承诺和同类自愿工具 | 自愿采用；可用于证明已采取措施，但不构成合规推定、确凿证据或安全港 |
| 标准化技术参考 | harmonised standards 的官方引文、共同规范、标准化请求、ISO/IEC/CEN/CENELEC 或行业框架 | 只有法律明确纳入或引用时才产生相应法律效果；标准全文不作为独立法源下载或引用 |

同一主题必须先写强制性法规底线，再另列解释性材料和建议良好实践。CoP 中的 will、encouraged、may 只表示自愿承诺的强度，不得翻译成独立的“应当”法定义务。

## 透明度机器可读落地基线

Art. 50(2)的法律底线是：在技术可行范围内，输出以机器可读格式标记，并可检测为人工生成或操纵；技术方案应当有效、可互操作、稳健、可靠。法律没有指定唯一格式，也没有自动要求所有内容采用元数据加水印双层方案。下列是给业务和工程团队的建议实现，不是额外法定义务：

1. 生成时建立唯一内容记录：provider 或平台标识、系统和模型名称及版本、生成或修改时间、内容唯一标识、是否 AI 生成或修改、输入内容哈希或父资产引用、输出模态和安全审计编号。
2. 采用可验证的来源数据容器，例如在适用媒体中保留 C2PA 或其他被业务选择的开放格式，并在图像、音频、视频、文档和结构化 API 输出中分别映射到 XMP/EXIF、ID3/RIFF、MP4 或 JSON 载荷。格式选择应当记录版本、签名算法、密钥轮换和兼容性测试结果；不要把某一行业格式写成法律唯一答案。
3. 对高风险丢失场景设置第二层可感知或不可感知标记，例如水印、音频标记或界面提示。该层是风险控制建议；是否需要以及采用何种层数，应当根据内容类型、成本、技术可行性和法律例外记录理由。
4. 在 API 响应中提供稳定的 `provenance` 对象或等效字段，并提供公开验证端点。验证端点只返回必要的来源信息，避免暴露个人数据或商业秘密；下载、转码、裁剪、编辑、缓存和跨平台发布时应当测试标记是否保持。
5. 记录标记写入、签名、验证失败、用户导出和人工覆盖事件。对外界面用自然语言说明“这是 AI 生成或修改内容”；机器字段供平台、监管机关和下游工具读取，不能用机器字段替代面向自然人的清晰披露。
6. 对中国大陆、欧盟和加州的字段要求建立映射表。若同一字段满足多个法域，统一生成并保留版本化 schema；若字段仅是 CoP 或行业建议，标注为建议字段，不把它升级为法定字段。

## 未来生效义务

报告中的“尚未生效”不得写成“当前不适用”。必须同时写：主体或系统是否已经落入定义、义务的法定生效日期、在生效前是否建议准备、以及日期变化时的复核动作。日期以最新 Official Journal、正式法规或州法文本为准；指南、CoP 的目标日期只标为建议节点。

## 业务反馈格式

最终先给一段自然语言结论，直接回答“当前做法是否存在风险、最先改什么、谁负责、何时完成”。随后给出一段集中列示的法律依据，并把每项依据标明效力标签。建议措施和合规评估不能只用代码、编号或表格短语表达。每个触发的法域都要说明最严重的已知后果；若事实不足，写明“无法确定”及需要补齐的证据。
