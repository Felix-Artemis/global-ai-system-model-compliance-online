# 三层角色映射

角色必须由事实决定。产品名称、模型供应商名称、合同标题或“我们只是技术提供商”的自称都不是充分依据。每个角色结论至少列一条定义依据和一条义务依据；不确定时标为conditional并按最严格路径预警。

## 一、价值链事实

先记录以下事实，再映射角色：

1. 谁开发或委托开发模型/系统。
2. 谁控制模型权重、训练、微调、更新和安全设置。
3. 谁以自己的名称或商标投放市场、投入使用或向公众展示。
4. 谁决定预期用途、客户群、营销和默认配置。
5. 谁实际操作系统、控制输入数据、接受输出影响。
6. 谁进口、分销、托管、提供API、运行应用商店或提供客户支持。
7. 谁决定处理个人信息的目的和方式，谁仅按指令处理。
8. 谁制造产品、组件、软件更新或承担召回/维修。

## 二、EU AI Act角色

| 事实模式 | 可能角色 | 主要锚点 | 不确定时 |
|---|---|---|---|
| 开发或委托开发并以自己名称/商标投放AI系统或模型 | provider | Art.3(3) | 若品牌/投放事实不清，按provider路径条件预警 |
| 在自己权限下使用系统（非个人非职业活动） | deployer | Art.3(4) | 记录实际运营方，不按购买方自动判断 |
| 欧盟境外主体把带第三国名称/商标的系统投放欧盟市场 | importer | Art.3(6)、Art.23 | 核实欧盟设立地和投放行为 |
| 供应链中使系统在欧盟市场可得且不是provider/importer | distributor | Art.3(7)、Art.24 | 核实实际供货和控制 |
| 欧盟境内接受书面授权代表provider履行义务 | authorised representative | Art.3(5)、相关条款 | 没有有效书面授权则不能假定 |
| 将模型集成到自己提供的AI系统 | downstream provider | Art.3(68)、Art.25 | 以自己名称投放或重大修改时按provider条件评估 |
| 自研/委托开发并以自己名义投放GPAI模型 | GPAI provider | Art.3(63)、Art.53 | API接入本身不自动成为上游GPAI provider |
| 供给模型/API/工具/数据或进行重大修改的价值链主体 | third-party/value-chain actor | Art.25 | 通过书面协议核实协作和信息责任 |

### 高风险重新归责

分销商、进口商、deployer或其他第三方如果以自己的名称投放、进行重大修改或改变预期用途使系统成为高风险，可能被视为provider。重大修改的训练算力三分之一标准只是官方指南指标性参考，不能单独决定角色。

## 三、第一层透明度角色

### 中国大陆

根据具体中国法规区分深度合成服务提供者、互联网信息服务提供者、生成式人工智能服务提供者、内容生产者和平台运营者。不要将EU provider/deployer直接翻译成中国法定角色；必须引用中国法定义和义务条款。

### 欧盟

Art.50(1)/(2)主要规制provider，Art.50(3)/(4)主要规制实际deployer；纯API提供者没有与自然人直接交互界面时，交互告知事实应由实际呈现界面的主体核实。透明度CoP角色承诺另标为欧盟建议的良好实践/解释性材料。

### 美国加州

按CAITA现行法核对covered provider、GenAI hosting platform、large online platform、capture-device manufacturer等定义、门槛和义务日期。开放注册、公开下载或平台托管不能仅凭企业客户标签排除公众可达；门槛数据不确定时按最严格路径预警。

## 四、GDPR角色

| 实际事实 | 角色 | 关键文件 |
|---|---|---|
| 决定处理目的和方式 | controller | Art.4(7)、Art.5-6、13-15 |
| 与另一方共同决定目的或方式 | joint controllers | Art.26安排 |
| 按控制者书面指令处理 | processor | Art.4(8)、Art.28 DPA |
| 代表处理者继续处理 | sub-processor | Art.28授权和流转 |
| 仅提供技术但仍为自身目的使用数据 | 可能是独立controller或joint controller | 按实际用途重判，不能只看合同 |

同一主体可在不同目的下拥有不同角色，例如售后是处理者、模型训练是控制者。逐目的判断，不得一份总合同覆盖所有目的。

## 五、CCPA/CPRA角色

按实际控制和用途区分business、service provider、contractor、third party。向外部模型供应商传输数据并不自动是service provider；如果供应商为自身训练、广告、跨客户画像或出售使用，需重新核对sale/share和独立business责任。

## 六、PLD角色

识别制造商、软件/组件制造商、产品进口商、授权代表、分销商、履约服务商及重大修改者。云端软件、SaaS和持续更新可能进入产品和控制范围，但责任仍需缺陷、损害和因果关系三要件。

## 七、角色输出格式

每个角色用以下字段输出：

角色名称；事实依据；定义条款；义务条款；当前状态（confirmed/conditional/unknown/not applicable）；strict_trigger（true/false）；需补证材料；责任部门；上线阻断条件。

不要输出“供应商负责所以本公司没有义务”这类无条件转移结论。上游合同只能作为分工证据，不能自动消灭法定责任。
